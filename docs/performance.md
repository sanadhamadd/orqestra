# Performance

This page reports what the benchmark harness (`benchmarks/`) measured on one machine, and what
the measurements show. The tables are generated from the committed result files under
`benchmarks/results/`. The analysis cites the files and the metrics behind each statement.
Values computed from measurements are labelled as derived, with their formula. How to run the
harness is in the README, [Running the benchmarks](../README.md#running-the-benchmarks).

## What was measured and how

The workloads are synthetic.
- **`invoice`:** the invoice verification workload, with tasks of 10, 100 or 1,000 invoices. It
  runs on an offline provider double, so nothing here measures a real provider's latency, cost
  or reliability.
- **`echo`:** a task that returns its payload, so a cell measures the engine alone.
- **`wait`:** a task that sleeps 50 ms, so a cell is handler-bound.

Everything ran on one Apple M3 Mac with 8 cores and 8 GiB of memory. PostgreSQL 16.15 ran in
Docker, from the pinned image digest, on a dedicated Compose project (`orqestra-bench`) with a
fresh volume and its own database, reached over loopback. Nothing else used the machine. The
server settings and the Docker VM's size are recorded in each result and shown above each table.
The worker settings are measurement values, not recommendations (DEC-034); they are recorded in
each result file too.

Each ladder interleaves its repetitions by worker count. Every figure in the tables is the
median of three repetitions, with the minimum and maximum. The warm-up and the 50,000-invoice
rung ran once each, the second by the owner's ruling (OD-2). Every result was measured on commit
`c410ac6` from a clean tree. Every cell and drill ended `complete`; none was re-run.

What each figure covers:
- **Database CPU and lock waits** are sampled from the submission to the end of the wait for the
  job, and each summary records its window (`resources.database.window_s`,
  `contention.window_s`). The lock-wait samples leave out the harness's own connections.
- **Commits per task** is an estimate: the `xact_commit` delta over the job, less the workers'
  idle claims before and after it at the idle claim rate measured after the job. It includes the
  submit command's own few commits. Each end can be off by about one second of idle claims,
  because PostgreSQL publishes its counters at most once a second. The method is stored in each
  file (`database_stats.commits.method`).
- **Claim cost** is measured on a table rewritten by `VACUUM (FULL, ANALYZE)` for every variant,
  and each measurement records the table's size in pages (`heap_pages`).

The steps, in the order they ran, each with `ORQESTRA_BENCH_DATABASE_URL` set to the dedicated
database:

```bash
uv run python -m benchmarks.ladder warm-up --db-container orqestra-bench-postgres-1
uv run python -m benchmarks.ladder scale --db-container orqestra-bench-postgres-1
uv run python -m benchmarks.ladder overhead --db-container orqestra-bench-postgres-1
uv run python -m benchmarks.ladder handler-bound --db-container orqestra-bench-postgres-1
uv run python -m benchmarks.ladder batch --db-container orqestra-bench-postgres-1
uv run python -m benchmarks.claims --out benchmarks/results/claims/20261109T011052Z-c410ac6-claims.json
uv run python -m benchmarks.drills d1   # then d2, d3a, d4, and last: d3b --allow-db-restart
uv run python -m benchmarks.ladder large --workers 8 --repetitions 1 --db-container orqestra-bench-postgres-1
```

## Analysis

The method is the agreed one: scaling, engine overhead per task, attribution, claim cost and
write amplification. Unless a paragraph names another file, the figures it gives are table
values (medians of three repetitions). Database CPU, lock waits and table counters are read
from the same result files, under `resources.database`, `contention` and `database_stats`, and
are given as the median over a cell's repetitions.

### Scaling

**Handler-bound work.** The hypothesis was that `wait` scales almost linearly, because each
task sleeps and uses no resource the workers share. The data confirm it.
- Derived: S(W) is 2.02, 4.08 and 8.74 at 2, 4 and 8 workers, an efficiency of 1.01 to 1.09.
- Files: `*-wait-400-b0-w{1,2,4,8}-r{1,2,3}.json`.

**Engine-bound work.** `echo` scales sub-linearly.
- Derived: S(W) is 1.82, 2.87 and 4.13, an efficiency of 0.91, 0.72 and 0.52.
- Files: `*-echo-10000-b0-w{1,2,4,8}-r{1,2,3}.json`.

**Invoices.** At batch 100, `invoice` scales least.
- Derived: at 10,000 invoices, S(8) is 2.56 with an efficiency of 0.32. The 1,000-invoice and
  5,000-invoice ladders give 1.95 and 2.37.
- Measured: median throughput at 10,000 invoices goes from 3,901.5 items/s at one worker to
  9,988.9 items/s at eight.
- Files: `*-invoice-10000-b100-w{1,2,4,8}-r{1,2,3}.json`.

### Engine overhead per task

The formula, derived: makespan × W ÷ tasks − median service time p50.

**`echo`.** This measures the engine almost alone.
- Derived: 0.006 s per task at one worker, rising to 0.013 s at eight.
- Measured: echo's service time p50 is 0.002 to 0.004 s.
- Files: the echo files above.

**Against invoice service time.** At 10,000 invoices on four workers:

| Batch | Tasks | Invoice service time p50 (measured) | Engine overhead per task (derived) | Throughput (measured) |
| --- | --- | --- | --- | --- |
| 10 | 1,000 | 0.006 s | 0.009 s | 2,682.6 items/s |
| 100 | 100 | 0.031 s | 0.021 s | 7,763.4 items/s |
| 1,000 | 10 | 0.123 s | 0.156 s | 14,332.0 items/s |

At batch 10, a task's service time is smaller than the engine's per-task overhead, so the
engine's fixed cost per task dominates. Larger batches spread that cost over more items, and
throughput rises at each step. Batching is the lever for this workload.

At batch 1,000 the derived overhead exceeds the service time. The formula charges every
worker's whole makespan to the tasks, idle time included. Hypothesis, not tested here: with 10
tasks on four workers, most of that is workers waiting for the last tasks, not a per-task cost.

### Claim cost against queue depth

Claim latency grows roughly in proportion to the number of queued rows. Every depth and variant
scans `tasks` sequentially, then sorts, then locks the row (`LockRows`). The `ready` and
`waiting` variants join `jobs` with a nested loop; the `unsupported` variant uses a hash join.

| Variant | Claim latency p50 (measured) |
| --- | --- |
| All tasks eligible | 1.875 ms at 1,000 tasks; 6.403 ms at 10,000; 28.497 ms at 50,000; 54.677 ms at 100,000 |
| Half waiting on a later `available_at` | 32.218 ms at 100,000 |
| Half of a kind the claimant does not run | 34.742 ms at 100,000 |

The two half-eligible variants cost less because fewer rows are sorted, but every row is still
scanned. Every variant was measured on a table of the same size at each depth: 17, 164, 820 and
1,640 pages at 1,000 to 100,000 tasks (`heap_pages`). EXPLAIN execution time p50 tracks the
latency, at 58.881 ms for 100,000 eligible tasks.
